原级别问题原来什么毛病现在怎么修
P1 删图后文件夹关联成孤儿 触发器只清 item_tags / image_notes / faces，没有 image_folders；计数直接 COUNT(*) FROM image_folders 不 JOIN images → 侧栏张数虚高、封面可能指向已删图。 server/db.js 加 trg_image_folders_delete；server/folders.js 的计数与封面查询改为 JOIN images 双保险；迁移 v2 一次性清理旧孤儿。
P1 删图后评论永久残留 image_comments 既无外键也无触发器，删素材后评论正文一直留在库里。 加 trg_image_comments_delete，同一迁移里清历史残留。
P1 去重回滚 / 导入淘汰只删主表 library.js 三处与 bulk-import.js 的淘汰路径都只 DELETE FROM images，关联行与向量留着。 不逐个改调用点，改成由触发器统一兜住（含 trg_clip_vec_delete）：任何删除路径都干净，将来新增的删除代码也自动受益。
P1 abs_path 唯一索引可能根本没建起来 老库有重复路径时建索引抛错，代码只 console.warn 就继续，用户完全看不到保障已缺失。 状态入 getPathIndexState()，在「设置 → 数据与维护 → 库健康」显示「缺失 + N 组重复」，并提供重建索引按钮（POST /api/maintenance/path-index）。
P2 CLIP 查重失败被静默忽略 采集批量入库时 clip.embedImage 抛错只打日志，这批素材其实没做向量查重。 结果里新增 clipCheckFailed / clipCheckError，采集任务统计与日志里明说「本次仅按 pHash 查重」。
P2 relocate 的 stat 失败被吞 size = 0 让「大小 + 文件名」匹配退化成「文件名唯一即认」，可能张冠李戴。 拿不到大小就排除该文件并计入 unreadable，不再降级匹配。
P2 动态壁纸面板两处裸 catch 能力探测失败 → 整块说明无声消失；参数预览失败 → 「拖了没反应」。 能力探测失败显示行内告警；参数预览失败提示一次（用 ref 去重，拖拽时不刷屏）。
P2 hue 迁移裸 catch 列改名失败后两次 catch {}，颜色语义错乱且无告警。 迁移后直接查表结构核对类型与残留列，失败写入 schemaWarnings，在「库健康」里展示。
P2 人脸功能的三个半截口 灯箱看不到「这张图有谁」，误检的脸不能改派 / 删除，另有死路由 /api/face/persons/:id/images。 新增 web/src/components/lightbox/FaceChips.tsx（人名 + 改派 + 移除，无人脸时整块不渲染）；人物页加「清空数据」；死路由删除。
P1 [本轮后续] 三张关联表仍无删除触发器 image_quality / image_annotations / image_ocr 以 image_id 为主键，无外键无 trg_*_delete；去重回滚 / 批量淘汰 / 清空回收站留孤儿，CI 查不出（delete-cascade 只断言 3 张表）。 server/db.js 加 trg_image_quality_delete / trg_image_annotations_delete / trg_image_ocr_delete；迁移 v3 一次性清历史孤儿；delete-cascade 扩到 6 张表并断言 6 个触发器都在。

04明确不做的事

写下来是为了避免每轮都重新讨论一次；有异议时改这张表，而不是在别处另开一份结论。

项结论理由
账号体系 / 自建云图床不做与「原图在自己硬盘」的定位冲突；Eagle 用同步盘就够了。
实时行级协同编辑不做单机创作者不需要，做了会拖慢所有写路径。
引入 ffmpeg不做体积与分发风险大；现有纯 JS 方案（元数据、取帧、GIF89a、MediaRecorder）够用。
移动端完整编辑不做手机只做浏览、投送、只读分享，编辑留在桌面。
云同步 / 多端实时不做（已决策）只做「同步文件夹 + 版本快照」，两端显式发布 / 拉取，冲突明确报出。
Windows 之外的系统级壁纸挂载不做WorkerW 桌面层是 Win32 专有；macOS / Linux 降级为静态壁纸并说明原因。

06维护规则

  • 只维护这一份。原先的 项目总览.html 与 对标与优化报告.html 已合并删除；不要再按日期新建副本，也不要再拆成「台账 / 报告」两份。
  • 状态只有四种：已实现 / 部分 / 未做 / 已决策不做。写「部分」必须同时写清缺什么，否则等于没写。
  • 第 3 节分两段维护：上段是「已修的对照」（保留原来什么毛病 / 现在怎么修，方便同类问题复查），下段是「仍待修清单」。修好一条，就把它从下段搬到上段并写清修法与回归测试。

  • 数字必须可复跑。单测 / 冒烟 / 基准的数字只在 npm run verify 全绿时才允许往上改。
