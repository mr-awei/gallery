读法：TuKu 的 11 个 ● 里，有 4 个是别人集体缺席的（智能规则嵌套、桌面集成、扩展到 MCP、混合检索同时做）。唯一剩下的 ○ 是地图 —— 「不记得存哪」的两条退路里还缺这条。
另外「编辑默认不改原图」标 ◐ 而非 ●：打开非破坏模式后裁切 / 旋转 / 调色只记操作链、原图字节不动，但不打开时，有保存步骤的编辑默认存副本，旋转 / 增强 / 超分这类即时动作仍就地写回。
三条解读：
① 强项集中得刚好。性能、桌面集成、检索、预览这四项目标用户每天都要碰，它们都在 9 分以上；而 Eagle 的短板（桌面集成 5.0、跨端 3.0）我们并没有跟着短。
② 最大的结构差异不是功能数量，而是「浏览路径」。Photos / digiKam / Immich 都给了「时间线」这条不依赖文件夹的记忆路径，LR / digiKam 还给「地图」。时间线已有（年份 → 月份 → 当天，点进去直接回到那一段），缺的只剩「地图 / 地点」这一条。
③ 第二处结构差异基本持平。LR / Capture One / digiKam 默认不碰原图。打开非破坏模式后裁切 / 旋转 / 调色只记操作链、随时可调回；不打开时，有保存步骤的编辑默认存副本。仍写回原图的只剩增强 / 超分 / 擦除这类「结果本身就是新像素」的动作。

#6 地点视图（先做列表版，零底图）P1

「去年在大理拍的那些」这类需求现在只能靠搜索。GPS 已经在库里，缺的只是聚合与入口。

做法：按 lat/lon 以 0.05° 量化聚成「地点簇」，每个簇显示覆盖范围 + 张数 + 代表图三张；点进去是照片墙，点「在地图中打开」调系统浏览器（Bing/高德均可，只拼 URL，不嵌地图）。不用一个字节底图，也不联网。

1~2 天收益 高参考 LR 地图 / digiKam
#8 英文界面收口（剩余长尾）P1

界面主体已双语，剩下的是长尾文案，不是结构问题；决定这个库能不能给非中文用户用。

剩余：编辑面板内部的长句（水印工作室、调色室）、设置页分区正文（采集 / 画质 / 壁纸 / 网络等卡片的字段说明）、人物页工具栏、部分右键菜单。按页补即可；英文缺失时回退中文，不会出现空标签。

05明确不做（想清楚了，不再反复争）

写在这里是为了不再重新讨论。每条都注了理由，条件变了再翻案。

不做的事理由
云同步、移动端编辑定位是单机 · 一个远程 · 一个出口。跨端只做「文件夹同步 + 快照」和「手机投送 / 只读分享」。对标分因此停在「跨平台·云」3.0，是主动选择不是欠账。
RAW 显影（demosaic / 去马赛克）RAW 只读相机内嵌预览。自己做显影意味着色彩科学、镜头校正、降噪全套，且永远追不上 LR —— 收益低、维护重。
引入 ffmpeg视频靠纯 JS 探元数据 + 扫帧。打包体积与许可证都不可接受，宁可功能弱一点。
模板页（AI 自动排版）画廊服务艺术 / 摄影 / 杂志三种视觉方向，做模板会变成内容生意，偏离工具。
屏幕取色器系统已有工具，重复造。
覆盖层基础样式 + size 档位UI 已定型，改基础样式会动到所有页面，风险大于收益。
4K 壁纸自动适配全部只能人工重跑一次，自动化会被误判（裁掉主体）。
自研人脸模型用 SCRFD det_10g + ArcFace w600k_r50 公开权重，权重进可信哈希清单。训练不是本项目的活。

全绿 ≠ 没缺陷：这四套加手工核对能挡住「改坏了 / 契约破了」，挡不住「设计错了」。真实库的形状（同步盘、中文路径、删除失败、EXIF 缺失）永远比测试夹具野，所以别把全绿读成「没有待办」—— 该看的是 02 节那三件。

07维护规则（改这份文档之前先读）

  • 只写没做到的。已交付的功能、已修复的缺陷、已做完的机会点，一律从正文删除，去向是 README 变更日志 + git log。这份文档回答「还差什么」，不是功劳簿。
  • 每条必须按代码复核。「接口在 / 入口不在 / 只有批量」这类话都要能指到文件和函数，写完更新顶部日期。
  • 数字不要手改。npm run verify 末尾会自动回写 data-stat；手改的数字下一轮就会被覆盖。写新数字前先保证这一轮真的全绿。
  • 分数改动三处同步：README「对标速览」、本文档 00 节 KPI 与雷达图、README 变更日志。
  • 机会点做完后：删卡片、删 02 表对应行、在 README 变更日志记一条，并把机会点编号往后顺延不重排（锚点稳定）。
  • 对标要更新：每轮复核时至少抽查 Eagle 与 Immich 的公开更新记录，别拿两年前的功能表对今天的对手。
