01

结论速览：单机第一，远期目标也够到第一

先给答案，再给证据。三块内容分别回答：凭什么单机第一、四项远期目标各值多少分、这套分数该怎么读。

凭什么单机第一

  • 数据模型是"素材库"而不是"相册"：40 张表、真外键约束、FTS5 trigram 全文索引，设计稿 11 种、RAW 40+ 种、三维 9 种、EPUB 电子书都能进库并出缩略图。
  • 自动化是原生的：10 个采集源、11 个 MCP 工具、插件沙箱、REST 带 token 与 scope、172 条内置教程——同行普遍只有"导入 + 拖拽"。
  • 桌面集成到系统层：托盘、可改全局热键、Windows 动态壁纸（WorkerW）、拖出到资源管理器、右键采集、局域网只读分享。

四项远期目标各值多少分

  • 云与多端 15 → 80（权重 9）：先账号与只读多端，再增量同步与移动端；兑现 +5.85。
  • 协作与社区 20 → 60（权重 8）：评论、分享、最小权限闭环；插件市场不作承诺；兑现 +3.20。
  • 多语言 5 → 90（权重 5）：先把界面文案抽成词条，再上翻译层；兑现 +4.25。
  • 跨平台 20 → 85（权重 4）：mac 真机冒烟 + 安装包，Linux 顺延；兑现 +2.60。
  • 四项合计 +15.9：71.2 → 87.1，从第 3 升到第 1。顺序与前置条件见第 09 节。

一句话结论

如果你是一个人、一台 Windows、一个几万到几十万张的本地素材库，它是当前性价比与可控性最好的选择； 这四项远期目标是真会做的方向，但顺序由现实约束决定——个人项目、没有服务器预算、单平台维护成本—— 所以别按"下个版本就有"去预期。

现在适合：设计师个人库 / 摄影后期素材池 / 素材收集与归档 / 需要被脚本和 AI 调用的工作流。
现在还缺：团队共享、跨设备同步、出海多语言界面——它们写在路线图上，不在今天的安装包里。
三档口径，全部百分制，而且分母一致（17 维 100 分权重）： ① 71.2 = 现在（四项平台能力按今天的进度计，第 3）； ② 76.4 = 中期目标（多端只读 + mac 真机 + 权限雏形，第 2）； ③ 87.1 = 远期目标（四项按 80 / 60 / 90 / 85 的目标值计，第 1）。 三档是单调上升的：71.2 → 76.4 → 87.1，远期目标不会低于现在。 另外还有一把尺子：单机专项 90.9（13 维 100 分，只把已实现能力计入，用于和竞品比"本地管理器"）。 它的分母里去掉了那 26 分尚未兑现的平台权重，所以 90.9 与 87.1 不可直接相减——同一口径下对应的就是 71.2。
读数约定：90 分以上 = 接近同类商用上限；80–90 = 成熟可交付，只剩打磨； 70–80 = 能用但明显弱于头部；60 以下 = 结构性缺口，不是补丁能解决的。 上一版 90.0 与本版 90.9 的差异来自两处实质补强：主网格布局计算从 O(n) 全量重排改成增量追加 + 底边分桶， 以及 AI 夜间批处理队列（语义与人脸索引挪到闲置时段串行补算）。 17 维当前分因此从 70.6 到 71.2——越过 PhotoPrism（70.5），离 Eagle（71.8）还差 0.6。 分数一律直接用百分制，不再用"10 分制小数"表示：写 9.00 容易被读成"100 分只拿 9 分"。

评分方法：13 维算现在，4 维算远期

先把"怎么算"摊开，分数才有讨论价值。全部维度直接按 100 分打分再按权重加权：前 13 维构成单机基准（100 分，只算已实现能力）； 后 4 维是长期平台能力，按"当下的值"与"目标值"各算一次，就得到 71.2 与 87.1。 加权就是"维度分 × 权重 ÷ 100"再相加，所以每个维度掉 1 分，总分掉 0.02–0.09 分。

为什么这样配权重

  • 单机基准 假设用户只有一台机器、一个库、自己一个人用。那么决定日常体验的就是"能不能快速找回来"——组织 10 分 + 检索 12 分是全场最高权重，性能 9 分紧随其后。
  • 远期 17 维 假设有一天要拿去和 Immich 这类"能装下一整个团队"的产品比。这时同步与协作合计 17 分、多语言与跨平台 9 分，前 13 维被稀释到 74 分——四维按今天的进度计是 71.2，按目标值计是 87.1。
  • 两个口径都不奖励 PPT 功能：AI 维度要求本机可跑、有失败回退；性能维度要求有基准脚本可复现。

打分怎么保证不飘

  • TuKu 的每一分都能复核：要么有代码位置，要么有 npm run bench:quick 的实测数字。
  • 竞品分数是公开功能面的估算，不是厂商官方数据。同档位不超过 93，除非有可复现的实测。
  • 不确定就往低打：例如 Eagle 的自动化能力，公开资料只到"插件 API"，因此给 65 而非 80。
  • 8 个竞品全部用同一份问卷、同一组锚点打分，避免"给对手挑刺、给自己放水"。

竞品各自强在哪（只讲事实）

  • Eagle：本地素材库的老牌标准。格式预览深度、界面手感、模板生态最好，设计师群体的默认选择；弱在自动化与开放接口。
  • Immich：开源自托管相册的标杆。移动端、多用户、多语言、同步几乎满配；弱在"素材"而非"照片"——设计稿、RAW、桌面集成基本不覆盖。
  • PhotoPrism：照片管理型。检索与自动整理强，编辑与导入体验弱，定位偏"个人照片库"。
  • Billfish / Pixcall：国产本地素材工具，易用性尚可，自动化、AI 与格式支持明显薄于前两者。
  • Bridge / XnView：Adobe 配套与看图工具，胜在轻量与格式，谈不上"库"。

三条最该记住的对比

单机（90.9）：领先 Eagle 8.8 分。差距不在界面，而在三处 Eagle 没做的事—— 网络采集与脚本接口、本机 AI（CLIP + 人脸聚类 + HNSW）、数据出口（XMP / 备份校验 / 双栈撤销）。

17 维口径现在（71.2）：落后 Immich 7.0 分。已经越过 PhotoPrism（70.5）， 离 Eagle（71.8）只差 0.6；中期目标 76.4 能追到第 2，但仍差 1.8——差的正是账号、变更合并、移动端与翻译层。

远期目标（87.1）：反超 Immich 8.9 分。同一把尺子下，现在 71.2 → 远期 87.1， 涨 15.9 分；四个目标值（80 / 60 / 90 / 85）都能逐项验收，达标才算数。

换句话说：单机它已经是领先者，平台能力是待兑现的路线图。两个判断可以同时成立。

05

真正的优势：十件"别人没做"的事

这一节只收录能落到代码或实测数字的优势。凡是"体验不错""界面好看"这类主观项，一律不进榜。

01采集面是同类里最宽的

10 个网络采集源，加上文件夹监听、ZIP、剪贴板、拖拽、浏览器右键、手机网页上传——入口多到可以按"我当时在哪儿看见这张图"来选。

证据：server/crawler.js SOURCES 表 · extension/ · 断点续采写入 jobs 表

02组织模型是"库"不是"相册"

文件夹树、标签树、集合、书签、播放列表、人物、地点、时间线八套视图共用一套索引，素材可以同时属于多个维度而不复制文件。

证据：server/db.js 40 张表 / 15 个触发器 / 37 个索引（外键接管了原来的级联触发器）

03检索是四路并行，不是四个按钮

FTS5 trigram 让中文子串也能命中，语义检索补"我记得画面但忘了词"，颜色与相似图补"我要找同款"。四路结果能叠在同一组筛选里。

证据：实测关键词 13ms、标签筛选 12ms、/api/tags 5ms（2 万级库）

04AI 完全跑在本机

中文 CLIP 语义、ONNX 人脸检测、HNSW 近邻、本地零样本标签——没有 API Key、没有上传、断网可用。这是同类里少见的取舍。

证据：server/clip.js · lib/hnsw.js · lib/face-math.js；2 万条向量检索 47ms

05自动化接口是产品的一部分

REST 带 token 与 scope、11 个 MCP 工具给 AI 客户端直接调用、插件走 manifest 权限白名单再进 node:vm 沙箱。素材库能被脚本和 Agent 当数据源用。

证据：server/mcp-server.mjs · lib/plugin-host.js · lib/plugin-manifest.js

06桌面集成扎到系统层

托盘、可改全局热键、开机自启、单实例、拖出到资源管理器、右键采集，以及 Windows 的动态壁纸（WorkerW + GLSL）。这是网页型产品结构上做不到的。

证据：electron/main/ · 全屏检测后自动暂停壁纸 · 失败回落静态图

07数据不锁死

XMP sidecar 双向、CSV/JSON/HTML 导出、带校验的备份与恢复、回收站、撤销/重做双栈（200 步 / 2GB 上限）、局域网只读分享带密码与过期。

证据：lib/undo.js · lib/lan.js · 备份排程 lib/backup-schedule.js

08编辑是非破坏的，而且能对账

裁切、旋转、调色、擦除、超分、水印、拼接都写成 edit_ops 操作序列，原图不动；调色预览与最终成品的像素结果一致，不是"预览好看导出翻车"。

证据：routes/edit* · 撤销走同一套操作栈 · 720p 调色 23ms / 1600px 71ms

09有真正的质量闸门

DTO 契约 45/52 一致、单测 520 / 520、冒烟 143 / 143、基准 15 / 15，外加四道 typecheck 与一套 lint；npm run verify 一条命令跑完。

证据：package.json scripts · scripts/verify* · CI 与发版流程同源

10规模意识写进了实现

导入走 worker 池 + 批量事务，列表用 keyset 而非 offset 深翻，缩略图分级缓存，向量检索有索引不是全表扫——不是"先做出来再优化"。

证据：灌库 6154 行/秒；列表首页 p95 7ms、深页 11ms；CLIP 2 万 47ms

缺点：按"会不会出事"排序，不按"好不好看"

排序规则很简单：会让用户丢数据或打不开的排最前，其次才是掉分的，最后是长尾的。 好消息是先说结论——本轮审计没有发现 P0 级问题，崩溃与数据丢失这一类在前几轮已经清干净了。 本页保留 10 条清单做回归对照：6 条已落地（灰色标注，含验收口径），4 条未修——签名、真机验收、预览深度、平台化。

云与多端 · 权重 9

现在 15 → 远期目标 80（+5.85）。今天不是零：局域网只读分享（密码 / 过期 / 禁下载）、备份到任意网盘或移动盘、多资源库切换。

为什么排在远期：四项里唯一需要持续花钱的——服务器、带宽、存储、备份，按月计。个人项目没有这笔预算，也不该在没钱时先许诺数据安全责任。

兑现路径：先只读多端（手机/网页看图，不写入）→ 账号与增量同步 → 冲突合并。只读阶段就能拿到约 50。

达标判据：同一账号在两台设备看到同一批素材；离线可读；冲突有明确提示而不是静默覆盖

协作与社区 · 权重 8

现在 20 → 远期目标 60（+3.20）。今天能做的是导出包 + 只读分享链接；插件系统可承载小范围内部工具，只是还没人写。

为什么排在远期：协作的前提是账号、权限、变更记录——三样都在云那一项里。先做协作等于把云做一半，顺序反了。

兑现路径：分享链接加批注 → 成员角色（查看/编辑/管理）→ 审批流。插件与模板市场不作承诺：空市场比没有市场更伤。

达标判据：两个账号对同一集合有不同权限，每次改动留操作记录

多语言 · 权重 5

现在 5 → 远期目标 90（+4.25）。今天只做简体中文：没有翻译层，文案直接写在组件里；上一轮已把双语机制整体移除，本项从零开始。

为什么排在远期：它是四项里唯一不需要服务器和预算的，但成本是"把几千条文案抽出来并冻结"的大范围机械改动——和别的重构一起做才划算，单独做纯属浪费。

兑现路径：文案抽到资源文件 → 生成 zh-CN / en-US 词条 → 排版适配（长单词换行、日期与数字格式）。RTL 语言明确不支持。

达标判据：切到英文后无硬编码中文残留；日期、数字、单位按区域格式化

跨平台 · 权重 4

现在 20 → 远期目标 85（+2.60）。今天只验收 Windows；mac / Linux 有构建目标，但没有真机 CI，所以对外不宣称。

为什么排在远期：桌面集成（动态壁纸、拖出、热键、文件关联）逐平台实现，摊三份就是三份维护；没有真机就没有"支持"二字。

兑现路径：第 08 节第 2 项就是它的前置件——mac 真机跑 143 项冒烟 → 安装包与公证 → 平台差异清单；Linux 顺延。

达标判据：mac 上托盘/热键/拖出/文件关联均可用，且 CI 留有记录
为什么这些分数要标"目标值"：目标值是验收线，不是承诺书。 任何一项下调 1 分，17 维总分就掉 0.4–0.9（× 权重 ÷ 100），表里可以自己核。

为什么顺序是先跨平台与多语言，后云与协作：前两项是一次性工程，不吃预算，做完就固定在那里； 后两项是持续性支出（服务器 + 带宽 + 备份 + 值班），也是个人项目真实的财力边界。 所以路线图里写得清楚：先把不花钱的做完，再按收入决定云做到哪一档——这是取舍，不是能力问题。

互操作与"数据带走"：这是被低估的优势

素材管理工具最大的隐性成本是"用了三年，想换换不掉"。这一项在评分里只占少量权重，但对真实用户可能是决定性的。

元数据双向

XMP sidecar 读写，标签、评分、说明可以留给下一个工具读；原图始终是原图，编辑只写操作序列。

结构化导出

CSV / JSON / HTML 三种出口；HTML 画廊可直接内嵌分享，JSON 足够重建整库索引。

可编程访问

REST 带 token 与 scope、11 个 MCP 工具。换句话说：就算哪天不用了，脚本也能把数据搬干净。

还有一条经验值得写进来：Eagle 的 .library 目录里保留着原始副本，误改过的图可以按字节数比对找回—— 这类"对手的数据也能读"的能力，正是本地工具该有的样子。

方法、边界与免责

这次审计做了什么

  • 通读六个目录共 563 文件：路由与数据层、前端交互、桌面与自动化、测试与交付。
  • 用脚本统计规模、表结构、索引、触发器、依赖、包体、格式覆盖与测试数量，避免"凭感觉"。
  • 实跑 bench:quick 取 p95；实跑 typecheck / lint / unit / smoke 确认结论成立。
  • 三个分域深审并行（后端、前端、桌面与工程），交叉核对后才写进报告。
  • 8 个竞品用同一份问卷打分，锚点固定，不确定处一律往低打。

哪些结论还不够硬

  • 百万级未验收：性能数字来自 2 万级库，规模外推属于推断而非实测。
  • mac / Linux 未验收：只做了构建目标检查，没有真机跑过。
  • 竞品分数是估算：依据公开功能面，可能与实际体验有 ±3 分的偏差（百分制）。
