2 · P0 严重问题（必须优先修）

P0-1动态壁纸 web 模式把完整 desktopAPI 桥接暴露给任意远程网页
liveWindow 挂载 preload（openFolder/download/weiboLogin/screenCapture 等 12 个 API）却加载用户配置的任意 webUrl，恶意页面可读写本机文件、抓屏、窃取会话。
证据：electron/main.js:459-463, 578-581、electron/preload.cjs:3-22
修复：liveWindow 使用仅含 liveBus 的最小 preload，或按 URL 白名单决定是否挂桥接。
P0-2打包版 AI 模型缓存目录落入只读 asar → CLIP/超分首用必挂
cacheDir 解析为 app.asar\models（不可写）且 models/ 不在 build.files。
证据：electron/main.js(cacheDir)、package.json:66-76、server/clip.js:18、server/sr-deep.js:13
修复：cacheDir 改 app.getPath('userData')/models。
P0-3本地 API 无鉴权 + express.json limit:Infinity
139 条路由对任意本机网页开放（删除、清空回收站均可达）；单个大 POST 可打爆内存。
证据：server/app.js:188, 1762
修复：limit 设 '10mb'；启动生成随机 token 注入 preload，全部 /api 校验 x-gem-token。
P0-4微博 Cookie 明文入库并被 GET /api/settings 全量返回
证据：server/db.js:392-394、server/crawler.js:426、server/app.js:1630
修复：Electron safeStorage 加密；接口只回 hasCookie:true 掩码。
P0-5大图库无虚拟滚动 + CSS 多列瀑布流整列重排
items.map 全量渲染卡片永不卸载；column-count 追加节点触发全列重排，且顺序按列（时间序错乱）。数千张后掉帧——与 Eagle 差距最直观处。
证据：web/src/pages/Gallery.tsx:190-202、web/src/styles.css:428-437、package.json 无 virtual 库
修复：@tanstack/react-virtual 窗口化；瀑布流改 JS 按行分配绝对定位（保持时间序）。

7 · 逐家对标结论

vs Wallpaper Engine：差距在「内容与生态」——WE 有视频/音频壁纸、创意工坊、场景编辑器、Steam 更新通道；本项目仅有 Web 动态壁纸且无音频、无编辑器、无更新。胜出点：AI 增强（WE 完全没有）、多源采集、查重。动作：先补 electron-updater + 视频壁纸（SharpMPV/WebView 嵌 mpv 均可），音频可后置。

vs Lively Wallpaper：最直接的开源参照。Lively 的暂停规则更全（焦点/远程桌面/RDP），且有屏保模式、便携版；本项目 live 壁纸已有电池/全屏/锁屏暂停但轮换壁纸路径缺失（P1-9），且无自启/更新/日志。动作：轮换路径复用现有 isFullscreenAppRunning；补自启 + updater，即可对齐其桌面基线。

vs Eagle：图片管理体验差距最明显：Eagle 十万级库靠虚拟化与索引仍流畅，且有拖拽、右键、键盘优先、文件夹+标签+批注体系。本项目胜在采集与 AI（Eagle 无超分/语义搜索/偏好学习），但 P0-5 + P1-8 + P1-11 三项决定了「库大了以后用户会流向 Eagle」。动作：虚拟化 + tags 倒排表 + 键盘/右键三件套优先级最高。

vs wayper（AI 原生）：路线不同：wayper 是云端生成式（文生图壁纸），本项目是本地增强式（管理+AI 加工）。互补而非替代；若补一路本地/远端 txt2img（或接 SD WebUI API）即完成「生成→入库→去重→设壁纸」闭环，直接对位其核心卖点，且带独有查重与偏好层。

vs GitHub 开源壁纸管理器（Variety 等）：它们赢在轻量、配置可移植、CLI、自启/开机体验与 CI 发布纪律；本项目功能厚但配置不可导出、无 CLI、无 CI、README 过时。动作：补最小 CI（typecheck + electron-builder --dir 冒烟）与设置导入/导出。
